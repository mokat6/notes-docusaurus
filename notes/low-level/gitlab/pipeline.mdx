# 2 types of pipelines

1. Branch pipelines (normal one, on push commit)
2. Merge request pipeline
3. Tag pipeline

Any job with `rules` doesn't have configuration that excludes the job from the Merge Request pipeline.
When we start adding `rules`, we override default rules that would say the job shouldn't be part of the pipeline. If no job is in the pipeline, the pipeline doesn't exist.

workflow. Disable our pipeline, unless it's `main`

### disable artifact download

```yml
dependencies: []
```

means no dependencies, don't need to download artifacts. Otherwise dependencies you can put job name  
e.g. in unit test job

```yml
test_release_notes:
  dependencies:
    - release_note_job
```

Say previous stage has 2 jobs both with dependencies. Release notes and build. For this job I need only release_notes_job artifacts

Default behavior = always download all artifacts from all previous stages

### needs

Execute jobs out-of-order. Ignore stage ordering.

```yml
unit_test:
  stage: test
  needs: [] # doesn't need anything, it starts right away, in stage 2

test_app:
  stage: test
  needs:
    - build_app # as soon as build_app finishes in stage 1, this starts in stage 2. Other jobs in stage 1 continue to run.
```

Optimization. Might be harder to debug.  
Default is wait until a stage finishes, then the next stage

Gotcha:  
Only artifacts from needs array are downloaded. Indirect job artifacts don't get downloaded. Just add in needs.

```yml
deploy:
  needs:
    - job: build_app
    - job: test_app # doesn't produce artifacts
    - job: unit_tests
      artifacts: false # don't download these artifacts
```

So called `stageless pipeline`. Speeds up pipeline execution time.

# cache

Two jobs do `npm ci`. First job downloads node_modules and caches it.

```yml
default:
  image: node:22-alpine
  cache:
    key: my-cache
    paths:
      - node_modules/ # can only access current dir
```

In second stage job, test_sth still do `npm ci` it will just run through it very fast.  
Jobs must be able to run independently with or without cache.

Some people say, cache similar to artifact. You upload, then in other stage you download.  
But cache used for dependencies.  
Artifacts are essential to download. If you can't download artifact the job will fail. It's a dependency.

Cache - optimize performance  
Artifact - essential for the job to work.

Caching needs manual checking to make sure it speeds up the pipeline, not just adds overhead and makes it slower.

```yml
default:
  image: node:22-alpine
  cache:
    key: "npm-$CI_COMMIT_REF_NAME"
    paths:
      - node_modules/
```

```yml
default:
  image: node:22-alpine
  cache:
    key:
      files:
        - package-lock.json
    paths:
      - node_modules/
```

File is the key. File changed = invalidate cache

Disable cache downloading. For jobs that don't need node_modules. Like deploy_job

```yml
deploy_job:
  cache: [] # disables cache for this job
```

##### Cache policy

default: push and pull. Each job that has cache enabled, downloads and uploads. Might be not neccessary.

```yml
default:
  image: node:22-alpine
  cache: &global_cache
    key:
      files:
        - package-lock.json
      paths:
        - node_modules/

unit_tests:
  stage: test
  # Inherit global cache settings
  cache:
    <<: *global_cache
    # Override the policy
    policy: pull # only download cache, not upload
  script:
    - npm ci
    - npm test
```

Disable upload cache if nothing's changed, no need to upload

```yml
main_job:
  stage: build
  script:
    - npm ci
  rules:
    - changes:
      - package-lock.json
    variables:
      CACHE_POLICY: pull-push
    - when: always
    variables:
      CACHE_POLICY: pull
  cache:
    <<: *global_cache
    policy: $CACHE_POLICY
  artifacts:
   # ....
```
